调度系统要一个带禁止转向约束的有向路网最短路核算后端。调度员提交一组节点、若干条有向边和一批禁转规则，服务返回从起点到终点的最短路长度与经过的节点序列。范围限定在带禁转的图上最短路计算，仅经 HTTP 提供，没有网页，也不是外卖地图或骑手接单产品，与经纬度测地距离无关。

图的约定很明确：所有边长为正，本服务不接受负权。禁止转向用三元组 (from, via, to) 表达，意为不允许在节点 via 处从边 from→via 直接拐到边 via→to。为了正确表达禁转，最短路必须跑在「边的状态」或「节点加进入边」这样的扩展状态空间上，最后再把状态路径展开成节点序列；如果只在朴素的节点状态上搜索、忽略来向，就会让本该被禁的转向照样被走通，这是必须回避的错误。引用了不存在节点的请求、含负权或自环负权的图、指向不存在边的禁转规则，都要以带原因的错误 JSON 返回；起点终点之间无通路时返回明确的不可达标记。要内置一份小网格算例，其中禁掉某个左转，绕行的结果应当比不禁转时更长，供人启动后直接核对。

几条关系要同时成立并可测：完全没有禁转时，结果与普通 Dijkstra 完全一致；只新增一条禁转、且原最短路恰好用到了这个转向，新的最短路长度不小于原来的长度；把某条边的权重调大，最短路长度不会减少；当起点与终点相同时，长度为零、序列只有单个节点。

接口上要区分两类调用：一类给定图、起点、终点与禁转规则，返回最短路长度与节点序列；另一类在同一张图上，比较开启与关闭某组禁转两种情形，返回两个长度及其差值，让调度员看清一条禁转规则带来的绕行代价。服务常驻运行，同时到来的多个查询之间互不干扰，各自的搜索状态彼此隔离。

把图与状态建模、状态空间上的 Dijkstra、禁转规则表、路径展开、两情形对比、输入校验拆到独立模块，并配自动化测试，锁住无禁转时与朴素 Dijkstra 一致、加禁转后路径不变短这两条核心不变量，同时覆盖不可达与起终点相同的边界。

运行时定为 Node.js 20，代码全部以 TypeScript 撰写、编译为可直接执行的产物，接口层由 Express 承载，优先队列等结构自行实现或选用轻量依赖。交付上随仓库提供一个 Dockerfile，构建后的容器把服务绑到一个固定端口上，测试脚本同仓、可在容器内跑通。模块划分按职责来：图与状态建模、状态空间搜索算法、禁转规则处理、接口层各成一个文件，别把逻辑全汇到一处。
